# Legacy migration boundary

本模块用于替代 `addons_odoocc/occ_approval` 的实现，但不会删除或修改旧源码目录。
新旧目录的技术模块名都为 `occ_approval`，因此 addons path 必须保证新目录优先：

```text
addons,addons_occ,addons_odoocc
```

## 数据隔离

新引擎不复用旧状态机：

- 新流程使用 `occ.approval.workflow` 和不可变的
  `occ.approval.workflow.version`；
- 与旧模块重名的实例、节点模型显式使用全新的 `occ_approval_v2_*` 表；
- 新角色、任务、事件及多对多关系也使用独立的新表；
- 旧审批表和旧审批记录不会由本模块主动删除、更新或解释为新状态机记录。

替换同名模块后，旧 UI 和旧 Python 模型不再加载，但旧表仍保留在数据库中。需要长期
查询旧审批历史时，应在上线前确定只读归档、报表或独立迁移工具方案。

`19.0.1.1.0` 迁移会先停用旧模块遗留的定时任务、菜单、视图，以及对新旧同名实例模型
授予 `base.group_user` 全权限的旧 ACL；Odoo 在模块升级收尾时可能进一步删除这些已经不再
由新版声明的 XML 元数据。这些操作只针对运行元数据，不会删除旧审批表或业务记录。
安全 record rules 会在迁移中显式同步，并转为后续升级可维护的数据。

## 为什么不自动转换

旧定义允许数据库保存 Python 片段和任意方法名。直接迁移会把远程代码执行、权限绕过、
不可重复执行等风险带入新引擎，因此以下内容明确不导入：

- Python 条件或动态求值表达式；
- 任意触发方法名；
- 无法验证公司、用户和源模型边界的分配数据；
- 无法映射为新 DAG 和固定 connector action key 的运行状态。

未来若编写迁移器，只应白名单导入可验证的图结构、角色和分配关系；自动业务动作必须
重新实现 Python connector，并由管理员重新发布流程。

## 推荐上线步骤

1. 完整备份数据库和 filestore，并保留旧源码版本。
2. 在数据库副本中把 `addons_occ` 放到 `addons_odoocc` 前面后升级模块。
3. 检查旧表仍存在，新 `occ_approval_v2_*` 表为空且可正常创建数据。
4. 按业务逐个重建流程，使用 JSON Domain 替代旧 Python 条件。
5. 为非 `manual` 动作编写 connector，声明固定 action key，并验证递归保护。
6. 使用普通用户、审批人、管理员、跨公司用户和 Portal 用户分别做权限回归。
7. 验证 Dashboard、表单侧栏、归档流程历史入口、催办、超时和执行失败重试。
8. 若检测到同一源单据存在多个未结束的新引擎实例，或已批准实例仍有待执行、执行中、
   执行失败的业务动作，升级会中止并列出实例 ID；先人工完成、重试或取消冲突实例，
   不会由迁移脚本静默选择或删除。
9. 生产切换后将旧表保持只读，确认审计保留策略后再单独规划清理。

开发期 checksum schema 1 的已发布版本仍按旧 definition checksum 验证；新发布版本使用
schema 2，校验完整不可变版本快照。该兼容仅用于新引擎开发期升级，不代表旧模块 JSON
会被自动迁移。
